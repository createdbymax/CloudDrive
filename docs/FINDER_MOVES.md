# Finder moves

The earlier `.6` release introduced the original single-move worker, including destination timestamp proof, detached Finder eject and terminal errors for inactive retained moves. All 265 packaged Swift tests, 13 signed native checks and live eject passed; see [verification](FINDER_MOVES_VERIFICATION.md). The historical `.4` build passed scoped fixtures, but the later live Photos move stopped with retained recovery records. That move subsequently resumed and completed: the worker recorded 8,700 items, and a separate R2 check found the destination directory and no source directory. Finder moves require remote work, and move state is separate from the upload queue.

## Concurrent moves on one Mac

The legacy R2 worker tracks up to four moves on separate source and destination paths. It checks both ends for the same path, an ancestor, or a descendant before admitting another move. Moving two different folders into the same backup directory is allowed. Moving that backup directory while it contains an active destination must wait. Each accepted job has its own identity and recovery record. The first slot retains the original journal format and filename for upgrades.

On macOS, two ordinary NFS drag operations can wait on the same Finder parent directory before the second request reaches the worker. Use **Move to Folder…** in Finder’s CloudDrive menu or **Move Item…** in the dashboard to submit moves directly through the worker. Each action asks you to choose the destination. When a name is already in use, **Keep Both** lets you name the incoming item. The existing folder and incoming folder remain separate. Ordinary Finder replacement continues to follow filesystem rename semantics.

The protected action on R2 requires an absent destination object at copy commit. A saved receipt identifies the job, source version and target. The action supports individual files up to 5 GiB. Ordinary mounted moves retain the existing multipart path. R2's protected destination copy and source condition are documented in [Cloudflare’s S3 extensions](https://developers.cloudflare.com/r2/api/s3/extensions/). This drive supports one writing Mac. Another client changing the source between its final check and deletion can race a move.

Finder can keep a file or folder’s resource fork, tags and other Mac metadata in a hidden sibling named `._Name`. For example, moving `Projects` to `Backup/Projects` also moves a valid `._Projects` to `Backup/._Projects`. The CloudDrive action inventories that sibling, verifies the copy and records its progress in the same recovery journal as the selected item. It reserves both sibling paths while the move runs. An occupied destination sibling blocks the move. A source sibling whose contents fail AppleDouble validation stays in place.

The app mounts its loopback NFS volume with `hard,mutejukebox`. A long move can return repeated NFS “try later” replies. macOS otherwise lists that volume in **Server connections interrupted**. The mount option applies specifically to these replies. Genuine transport failures retain the normal macOS reporting. Changing an existing mount with `mount -u` was ineffective on the test Mac. Activation requires a normal eject and fresh mount.

A failed eject can briefly hide a volume from the kernel mount table while Finder still holds its files. The app records an attempted eject before calling macOS. If that attempt fails, it keeps the worker and its recovery information. For an eject initiated outside the app, it waits for repeated observations that the mount is absent, checks the NFS client and verifies the underlying local directory is visible. It repeats the checks immediately before stopping the worker. After a busy eject, close the open files or Finder window and retry eject.

## Behavior in the earlier single-move worker

- Files and folders move between parents within the mounted volume through one tracked native move job. While it runs, the rename RPC returns the NFS retry response (`JUKEBOX`); it does not report success before remote work and the final namespace/handle commit finish. Source/destination paths remain guarded. Existing unrelated directory handles and an independent native mount can continue reading and listing while the server works. macOS can still block path traversal through the rename parent on the same mount; this does not promise that every Finder window remains responsive. Native writes return busy rather than waiting behind the remote move.
- Folder moves retain NFS child handles and cached file identities. Unsupported disk/symlink handle-cache modes retain their upstream invalidation fallback; CloudDrive uses the default memory cache.
- The worker defers a move while its source or destination has open/dirty cache data. Leave the app running until uploads finish. Moves into the source's own subtree and incompatible/nonempty directory replacements are rejected before remote mutation.
- Inventory walking collects keys without fetching object metadata inside the walk callback. Up to eight metadata workers prepare the inventory, and preparation progress reports discovered/prepared counts. The inventory is bounded to 10,000 objects and 10,000 directories.
- R2 objects use server-side copy, including multipart copy for large objects, with up to four copy workers. A complete copy/receipt barrier and verification pass finish before up to four deletion workers remove sources. Payload files are not staged locally for this move path.
- Verification uses expected size, modification metadata, available MD5 and successful server-side copy receipts. Source identity keeps its original timestamp; a verified copy records the destination’s observed timestamp because S3 LastModified can legitimately change on copy. Recovery verifies that recorded destination identity before source removal. Older verified v1 receipts without destination timestamps retain their original source-timestamp expectation. Multipart ETags are not treated as whole-file MD5. Where the provider exposes no comparable checksum, this is not an independent cryptographic content verification claim.
- Active affected paths return the retry response. Once a move is inactive and needs explicit recovery, affected reads and blocked native writes return a terminal I/O error instead of retrying forever. Corrupt or foreign move records fail closed with a terminal error. Unrelated browsing remains available for a valid retained journal.
- A remote error retains a destination-bound manifest and synced per-object receipts in the private `Moves/<destination fingerprint>` directory under Application Support. Unrelated native writes are blocked until the move is recovered. Uploaded objects do not acquire a new remote storage format.
- Transfers, the menu and Finder recovery show move activity. Choose **Resume move** after resolving connection/permission problems. Recovery is explicit; polling does not mutate remote objects. A changed source or verified destination is preserved for diagnosis rather than deleted to force completion.
- An interrupted worker can be recovered/reconnected to read its move records. Direct uploads remain blocked for that destination until retained work is resolved. Eject detaches the Finder volume first and lets accepted cloud moves/uploads continue in the background. Healthy work has no 30-second drain deadline. Keep CloudDrive running; it automatically stops the owned worker only after fresh authenticated checks confirm uploads and moves are finished. Unknown, failed or unresolved work retains the worker and records; **Resume move** remains available for a retained move. Normal quit, reconnect and direct writers remain guarded until the worker has safely stopped. The existing **Quit App, Keep Worker** escape preserves the staged worker and recovery state. Recovery resumes monitoring a verified detached worker. Older workers without the move API retain their authenticated upload-idle shutdown checks.

## When Finder says items had to be skipped

On a worker older than the concurrent-move release, check CloudDrive’s move status before changing permissions. An unfinished move can block a rename elsewhere on the drive, even when its source files are writable. Resume the move named in CloudDrive and wait for completion. Then check whether the proposed destination already contains a folder with the same name. A native directory rename cannot merge two nonempty trees. Preserve both trees; do not delete the existing folder to make Finder accept the rename. To keep both folders, give the incoming folder a different name. To combine their contents, open both folders, compare duplicate names and copy the desired items individually. The legacy worker can reject a nonempty destination before it creates a move journal. Its older status response groups several rename failures under one message, so the app can offer a destination check but cannot identify that specific cause from this response.

## Limits

Folder moves are not remote transactions. During a failure, both old and new prefixes can contain objects. The app copies the full inventory before beginning source deletion, and resumes using retained receipts. Do not remove these records, clear the cache, or move/delete either prefix through another client while recovering.

There is no blanket ten-minute deadline for the whole folder. Directory-listing and metadata request groups have 30-second deadlines; each server-side object-copy operation has a five-minute deadline. An uncertain outcome is retained for explicit recovery, and trees beyond the inventory/record limits fail before copying. Remote work runs outside the short namespace/handle commit lock. Finder can still show Preparing while inventory and remote work continue; the app reports preparation progress. Slow-service qualification checks unrelated stat/read/list through an already open directory handle, plus root/folder access through an independent native mount, within three seconds during both inventory and copy pauses. These probes isolate server responsiveness from macOS rename-parent vnode locking; same-mount parent traversal can still wait. Concurrent external writers and multiple writing Macs remain unsupported. Cancelling Finder's progress dialog does not promise to reverse remote changes already accepted. Cross-volume moves remain a separate copy/delete workflow.

Saved move manifests and receipts contain private filenames and metadata, not credentials or payloads. Finished manifests are retained to recognize an immediately repeated completed rename; receipt files are metadata and may remain until subsequent maintenance. Keep the destination fingerprint unchanged while recovering; key rotation does not change the app-provided binding.

## Development qualification

```sh
python3 scripts/build-rclone-allocation.py
swift test
python3 scripts/qualify-finder-moves.py
python3 scripts/qualify-finder-moves.py --s3
python3 scripts/qualify-finder-moves.py --s3 --finder
python3 scripts/qualify-finder-moves.py --concurrent --independent-mount --finder
```

The S3 fixture independently verifies synthetic SigV4 requests, paginates listings, supports object and multipart copy, denies a source delete on demand, checks both copies survive and resumes through the authenticated control API. The responsiveness variant pauses inventory and copy independently, then uses an already open unrelated directory handle and a second read-only native mount to probe uncached unrelated stat/read plus root/folder listings with a three-second bound. A same-mount parent-path probe can wait in the macOS client while rename is outstanding; do not interpret the scoped test as proof that all Finder browsing is instant. A passed small move is not a substitute for those delayed-service checks. The native harness retains open descendant file/directory handles across a cross-parent move and checks contents and unrelated siblings. It never reads a saved connection or touches the user's mounted files. Failed fixtures retain private diagnostics; never remove a mounted fixture recursively.

A running worker is a digest-addressed executable staged outside the app bundle. Building or opening a newer app does not upgrade an already mounted worker. Detach the old Finder connection, wait for its accepted cloud work and owned worker to finish, then reconnect with the new build. Preserve unresolved records and recover them instead of forcing shutdown. Signed packaged tests and actual R2 tests are separate evidence; see [verification](FINDER_MOVES_VERIFICATION.md).

## App-card copies on the NFS mount

Worker `v1.75.2-clouddrive.8` supports competing exclusive **file** creates on a single mounted drive. In the loopback qualification, eight callers attempted to create the same file with different contents. Exactly one succeeded. Reading from the underlying storage independently confirmed that winner's bytes. The same run covered a normal write, rename, replacement, eject and remount. The file-create fix requires reconnecting to a worker with that capability.

A repeated NFS exclusive file-create request can succeed for the same verifier, path and server-observed inode. The worker retains the last 1,024 receipts. After eviction or restart a lost acknowledgement can leave a correctly created file visible while a retry reports that it already exists. Check the existing item before retrying under another name.

**Folder and package drops require a different guarantee.** Eight simultaneous mkdir requests on the same NFS target produced one server success and seven existence errors with distinct RPC transaction IDs. All eight callers nevertheless created their own uniquely named child in that directory on this Mac. Apple's NFS client treats a mkdir existence error followed by a successful directory lookup as a possible replay of a lost response. Consequently, even the fixed worker cannot use a successful macOS mkdir as proof that the app alone created that folder. A test where every contender writes an identically named child can mask this behavior. The NFS app-card path should accept regular files only until a separate owner-mediated directory publication passes independent competing-writer tests. [Apple NFS client mkdir handling](https://github.com/apple-oss-distributions/NFS/blob/93733ffccece4daee73bf6306b291d1ae69130c0/kext/nfs_vnops.c#L5695-L5711)

To qualify a candidate worker against a disposable local filesystem, run `python3 scripts/qualify-local.py --backend /path/to/rclone --check-exclusive-create`. The additional diagnostic flag `--check-exclusive-mkdir` deliberately exercises the directory ownership condition and fails on the macOS NFS client tested. FSKit is a separate mount implementation and needs its own concurrent mkdir qualification.
