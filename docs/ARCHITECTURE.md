# Architecture

The SwiftUI application delegate owns one `Drive` controller shared by the dashboard, native menu, Settings, Transfers and Recovery windows. Closing a window keeps that controller alive.

`Drive` owns the worker lifecycle. It starts a patched rclone backend, serves the chosen R2 prefix over loopback NFSv3, and mounts it using macOS `mount_nfs`. A separate bounded helper performs file operations that could otherwise block the UI. The application does not use a hosted CloudDrive account or proxy R2 data through a separate service.

Workers launch from private, digest-addressed copies outside the app bundle. Recovery validates the recorded process UID/start time/path, authenticated control PID, destination/cache binding, mount filesystem ID and NFS port. A recorded running worker is not compared against a newly rebuilt app’s backend; interrupted launch intents additionally require the original executable digest. Launch intent and session records support interrupted startup. An uncertain worker or mount is preserved for explicit recovery. Eject normally unmounts, checks/drains pending uploads, stops only the authenticated owned worker and confirms exit before retiring its record.

`ControlClient` uses authenticated loopback requests with deadlines, cancellation, response-size limits and no redirects/proxies. Queue identities, transfer counters and directional bandwidth readback are decoded strictly. Presentation does not treat malformed or stale samples as successful completion.

The backend uses full VFS write-back caching. Dirty/open data is retained; clean data is eligible for automatic eviction. Allocation patches expose the actual local payload cache allocation separately from logical remote size. Local physical-storage scans skip the mounted tree and do not hydrate cloud contents.

Direct uploads are a separate native path owned by `Drive.directUploads`. `DirectUploadController` binds the dashboard, Transfers and menu to an actor-owned `DirectUploadEngine`. The engine enumerates real source URLs; `UploadSourceReader` actors hold read access and serialize each source's seek/read/check operations. `S3MultipartRemote` signs path-style R2 S3 requests with CryptoKit SigV4 and uses an ephemeral foreground URLSession with capacity for eight connections; it does not send file contents through the NFS mount or create a disk payload spool. The batch scheduler defaults to four files (configurable 1/2/4/8) and four rolling parts per file, with global FIFO payload admission normally capped at 256 MiB. The cap rises only when a supported object's required fixed part size is itself larger. Destination-key leases prevent conflicting in-app publication, and one shared request-rate limiter applies across concurrent files. SQLite commits remain serialized and FULL synchronous. Revisioned/coalesced UI delivery cannot reorder queue states, and final state is flushed after request groups drain.

`UploadQueueStore` uses private, exclusively locked SQLite storage with full synchronous transactions and separate per-part rows. It persists destination binding, source identity/bookmarks, multipart upload ID, part sizes/checksums and final receipts. The default store is in private Application Support; the user may select an external records location. Records contain private metadata, not source payloads or R2 credentials. Recovery validates the original source, reconciles ListParts and saved checksums, and only uploads missing parts. Completion checks object size, upload-specific metadata and the expected multipart ETag; a lost completion response is reconciled before retrying.

`Drive.canConnect` excludes unresolved direct-upload work, and direct work requires a safely stopped Finder worker. Switching uses the existing eject/drain path. Window close retains the controller; active direct work blocks update installation and can pause before normal quit. These gates serialize writers within this app, not unrelated remote clients or multiple Macs. See [direct upload behavior and qualification limits](DIRECT_UPLOADS.md).

R2 keys are entered in the app and stored in Keychain. Child-process credentials are supplied through a sanitized environment, not command-line arguments or repository files. Worker control tokens and mount/recovery state live in owner-only application-support storage. They are runtime secrets and must never be exported with the project.

`experiments/streaming-nfs` is an independent prototype module with a private range journal and immutable synthetic S3 chunks. It does not replace this app architecture or change existing object formats.

The app-owned `CatalogController` opens an independent destination-bound SQLite metadata catalog at launch once a valid connection is loaded. `CatalogIndexer` consumes read-only paginated S3 inventory, commits page/token state atomically, and confirms missing candidates without changing remote objects. `CatalogStore` serializes SQLite work off the main actor; bounded FTS5 filename/path queries use only local metadata. Search does not traverse the mount or change worker/write ownership. Verified-upload outbox hints and an authenticated bounded worker feed drive automatic targeted updates, with revision guards and periodic reconciliation for gaps/outside changes. Finder acceleration and content extraction are later work. See [local search](LOCAL_SEARCH.md).

Finder moves use the optional native request/rename hooks and VFS safe-move patch. The default memory handle cache preserves identities and descendant paths, and VFS directory rename retains cached child nodes. `--vfs-move-journal` enables private destination-bound inventory plus append-only synced copy/delete receipts; `--vfs-move-binding` uses the app's stable connection fingerprint. R2 moves copy/verify the whole inventory before source deletion. Authenticated `vfs/moves` status and explicit asynchronous recovery remain separate from upload progress. Native mutation leases, retained-record checks and final move-state checks protect writer switching and worker shutdown. See [Finder moves](FINDER_MOVES.md).

The .4 native path returns a retryable NFS result while one journaled move runs in the background. Source/destination metadata guards preserve retry semantics; unrelated native requests do not share a long-held exclusive namespace lock. The exclusive namespace/handle commit occurs after remote work, before durable success is acknowledged. Successful native results are retained in a bounded replay history that supports macOS changing transaction IDs between retries, with source-creation invalidation. Inventory callbacks collect keys only, then bounded metadata/copy/delete pools run with individual request deadlines. macOS parent-vnode locking during rename remains a client-side limitation; the protocol does not acknowledge success before durable completion.
