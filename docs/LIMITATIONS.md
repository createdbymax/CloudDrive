# Current limitations

CloudDrive is an early development app for one user, one R2 connection and one actively writing Mac.

## Installed native Finder drive

Finder performs the transfers. Indexed folder moves change a parent/name locally and publish that change to R2 in the background. Finder can accept unrelated moves while publication is pending. A bounded writeback path handles a sequential copy larger than the available working space; the verified workload was 224 MiB with the entire working volume limited to 160 MiB. Local space is still needed for metadata and outstanding writes, and Finder can slow down while R2 catches up. A finished Finder progress bar does not certify remote publication.

Native tags, package copies, rename, concurrent independent moves, regular-file replacement, open-reader behavior, pin/free and safe reconnect have mounted tests. Arbitrary recursive merges, all extended attributes and permissions, days of sleep/wake or network interruptions, and every third-party editor are not covered. Name/path search is provided by the app; it is not a full-content Spotlight index. The native volume explicitly rejects creation of symbolic links and hard links. A project that embeds these needs separate handling. The app targets one actively writing Mac. Sharing and file requests are outside the personal-drive scope.

See [Finder and R2 measurements](helumi-parity-2026-11-05/07-FINDER-GROUPING-AND-R2-ADOPTION.md). The legacy notes below apply to a different mount implementation.

## Legacy NFS drive and direct uploader

- Legacy Finder writes stage the complete file locally before cloud upload. Large Finder copies can require their full size in temporary space. Cache size/reserve targets are soft limits for active/dirty data, not hard quotas. The separate [direct upload path](DIRECT_UPLOADS.md) streams original files into multipart requests without staging their payloads.
- Direct uploads require a writable private records folder and the unchanged original source file. Records can be placed on an external volume before queueing. A completely full macOS startup disk can still prevent ordinary OS operation; full-disk and full 400 GB upload qualification remain outstanding.
- Saved multipart progress can resume while the corresponding R2 session still exists. R2 normally expires incomplete uploads after seven days; custom bucket policy may differ. Expired parts must be re-uploaded after explicit restart. Confirmed multipart checksums and size are verified before an upload receipt is recorded.
- Direct uploads and Finder writes cannot run concurrently in this app. Pending direct jobs reserve the destination until completed or cancelled. Arbitrary outside writers and concurrent-Mac conflicts are unsupported.
- Direct upload supports resident regular files, at most 10,000 queued/history files, bounded folder scans, and R2's multipart object limits. Empty directories, packages, links, filesystem metadata and cloud placeholders are not preserved as a Mac backup. Unsupported items are reported. See [direct upload details](DIRECT_UPLOADS.md).
- Eligible uploaded/read cache data is automatically reclaimed. Metadata, active reads and pending uploads still use local storage. Originals outside the drive remain unchanged.
- Local search uses an automatically maintained metadata inventory. Outside-client changes and older running workers depend on periodic reconciliation. It does not search file contents, provide Finder/Spotlight indexing, or make uncached contents available offline. See [local search](LOCAL_SEARCH.md).
- On the legacy NFS drive, Finder deletion removes the remote object and overwrites can discard the previous bytes. On the native drive, explicit Recently Deleted actions support restore and permanent removal. The native drive also supports offline pinning and optional encrypted managed storage. See [installed feature verification](PERSONAL_DRIVE_COMPLETION_2026_11_05.md) for tested behavior by storage mode. Keep originals and use a dedicated prefix.
- Finder uses an NFSv3 server bound to loopback. Other processes/users on the same Mac can access that NFS listener; its data path does not have per-user authentication. The control API has separate authentication.
- Worker/mount ownership checks and bounded control calls preserve uncertain state instead of starting another writer or force-unmounting. A dead or unresponsive NFS worker can still leave native clients waiting and require recovery.
- The app blocks normal Finder quit until safe eject; active direct uploads offer an orderly pause-and-quit path. Window close leaves the app running. Force Quit, process termination, logout and power loss cannot be treated as normal safe shutdown; direct upload recovery must reconcile uncertain remote outcomes.
- Foundation allocation values and native Finder Get Info can differ or remain cached. Allocation patches preserve logical size and report available cache allocation; they do not guarantee that Finder refreshes immediately.
- Apple Silicon downloads are Developer ID signed and notarized. A complete long-duration workload/failure matrix and an update from a previously published notarized version remain unqualified. Manual Sparkle update checks and signed release preparation are implemented; see [release preparation](SPARKLE_RELEASES.md).

The separate streaming experiment proves early chunk upload and restart ordering using synthetic loopback services. It has restricted filenames/operations, explicit-only final publication, request/transfer amplification and a native worker-death waiting issue. It is not an app feature or a substitute for production qualification.

Finder folder moves use background journaled remote copy/verify/delete with retryable native requests and a short final namespace commit. Limits remain 10,000 objects/directories and a 32 MiB manifest. Metadata requests have 30-second bounds and each copy has a five-minute bound; there is no ten-minute whole-folder deadline. macOS can still hold a rename's parent directories until it receives the final result, so those directories can wait during a large move. Independent native mounts and already-open unrelated directory handles are separate responsiveness checks; this does not provide instant logical renames or atomic remote transactions. Partial moves retain records for explicit recovery. See [Finder moves](FINDER_MOVES.md).
